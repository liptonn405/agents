# CoderAgent: одно готовое поручение → изолированное редактирование

`coder_agent.CoderAgent` — новый независимый компонент для JSON-плана аналитика.
Он не выбирает Issue, не определяет причину ошибки, не запускает тесты Miminet,
других агентов, commit/push/merge/PR. Результат остаётся отдельным артефактом;
агент **никогда не применяет его к исходному репозиторию**.

Старые `developer_agent.py` и `main.py` сохранены без изменений. Их интерфейс
через Codex/Issue и тесты совместимы с прежней версией. Это отдельный legacy-режим
с прежними полномочиями; он не является адаптером нового контракта и не получает
описанные ниже гарантии изоляции. Новый CoderAgent его не вызывает.

## Структура

```text
agents/developer/
  coder_agent/
    contracts.py       Pydantic: вход, результат, ответ движка
    policy.py          доверенная конфигурация и запреты путей
    validator.py       согласованность плана и снимок входных файлов
    workspace.py       выборочный снимок, аудит, unified diff
    sandbox.py         монтирования и namespaces Bubblewrap
    bootstrap.py       лимиты процесса и loopback → Unix bridge
    engine.py          OpenCodeEngine и заменяемый Engine Protocol
    reports.py         flock, receipts, атомарные отчёты, состояние
    agent.py           одно выполнение без автоматических повторов
    __main__.py        CLI
    gateway.py         необязательный шлюз к одной модели
    build_runtime.py   сборка runtime из доверенных локальных бинарников
  examples/{task,config}.json
  tests/test_{contracts,policy,workspace,engine,agent,gateway,cli}.py
  tests/test_{engine_failures,recovery,runtime}.py
  tests/test_sandbox_integration.py
  tests/test_real_opencode_integration.py
  tests/{coder_support,sandbox_support}.py
  pyproject.toml
```

## Установка и подготовка

Нужны Linux, Python 3.11+, Pydantic 2.12–2.x, Git для исходного репозитория,
Bubblewrap с поддержкой `--unshare-user`, `--disable-userns`, `--size` и разрешённые
ядром user namespaces. Запускать от обычного пользователя. Docker не используется.
Установка пакета не устанавливает системные службы, Bubblewrap или OpenCode.

Из корня командного репозитория:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e ./agents/developer
```

Если окружение использует `uv` вместо pip:

```bash
uv venv .venv
uv pip install --python .venv/bin/python -e ./agents/developer
```

Заранее установите доверенный standalone-бинарник OpenCode согласно его
[официальной документации](https://opencode.ai/docs/). Агент ничего не скачивает.
Подготовьте **новый** runtime-каталог вне исходного репозитория и каталога запусков:

```bash
.venv/bin/python -m coder_agent.build_runtime \
  --root /absolute/private/coder-runtime \
  --opencode /absolute/path/to/trusted/opencode
```

Сборщик копирует выбранный OpenCode, текущий Python, стандартную библиотеку
и необходимые динамические библиотеки. Он использует `ldd`, поэтому входной
исполняемый файл должен быть доверенным. Скрипт не поддерживает npm-wrapper
вместо standalone-бинарника. Не указывайте `/`, домашний каталог или весь `/usr`
как runtime. Проверьте содержимое и права: в runtime не должно быть секретов,
проектов, пользовательских плагинов или конфигурации авторизации.
Расположение Python и stdlib сохраняется для согласованного prefix/RPATH;
`/usr/bin/python3` внутри runtime — относительный alias на скопированный Python.
Инсталляции Python под `/home`, `/tmp` и другими приватными mountpoints
отклоняются до сборки: используйте системный Python из `/usr` или `/usr/local`.

## Канал к модели

Сеть песочницы полностью отделена от хоста. Единственный внешний канал —
явно смонтированный Unix-сокет **выделенного модельного шлюза**. Передавать Docker,
SSH-agent, произвольный HTTP-прокси или другой служебный сокет запрещено.
Назначение сокета — доверенная настройка оператора, его нельзя установить планом.

В комплекте есть необязательный шлюз, запускаемый обычным процессом в переднем
плане. Например, для уже работающего локального OpenAI-compatible сервера модели:

```bash
mkdir -m 700 /absolute/private/coder-gateway
.venv/bin/python -m coder_agent.gateway \
  --socket /absolute/private/coder-gateway/model.sock \
  --upstream http://127.0.0.1:8080/v1 \
  --model local-model --max-requests 100 --max-tokens 8192
```

Шлюз принимает только `POST /v1/chat/completions` для фиксированной модели,
ограничивает число запросов, размер тела, ответа и запрошенный лимит токенов;
не принимает CONNECT, перенаправления или выбранный клиентом адрес. Для удалённого
сервера разрешён HTTPS. Если сервер требует ключ, только отдельный процесс шлюза
может получить `CODER_MODEL_API_KEY` из доверенного окружения оператора: ключ не
передаётся OpenCode. Настоящие ключи при разработке/тестировании не использовались.
Шлюз не ведёт журналы запросов и не устанавливается как системный сервис.
Ответы с ошибками upstream заменяются собственными ограниченными JSON-сообщениями:
их исходные тела и заголовки не передаются OpenCode. Одновременно допускается
до 16 соединений, есть тайм-аут до чтения HTTP-заголовков и защита общего бюджета
запросов между потоками. Допускается только один вариант ответа (`n=1`).

В доверенной конфигурации `model_context_tokens` описывает окно модели,
`model_output_tokens` — предел её ответа (по умолчанию 131072 и 8192).
Последний должен быть не больше `--max-tokens` шлюза и окна модели. Эти значения
передаются в OpenCode через `provider.models.<model>.limit`: без явного output
реальный OpenCode может запросить больше токенов, чем разрешает шлюз, и получить
`BLOCKED`. Сужать или повышать бюджет входной JSON аналитика не может.

Нужен сервер, поддерживающий streaming chat completions и tools. Совместимость
конкретной модели/провайдера следует отдельно проверить в тестовом окружении.
OpenCode использует встроенный адаптер `@ai-sdk/openai-compatible`; версия,
которой потребуется скачивание SDK, в закрытой сети работать не сможет.

Для бесплатной Ollama подготовлены пользовательская установка и воспроизводимые
проверки: [локальная модель](LOCAL_MODEL.md). Платные API и ключи не требуются.
Доверенный `model_request_timeout_seconds` (по умолчанию 60, максимум 7200)
задаёт таймаут чтения модельного канала и ограничивается общим сроком задачи.
Согласуйте его с `--upstream-timeout` шлюза для холодного запуска локальной модели.
Необязательные `model_reasoning_effort` (`none`, `low`, `medium`, `high`) и
`model_temperature` (0–2) передаются в конфигурацию OpenCode; поддержку конкретных
значений проверяйте у модели. Эти настройки не меняют файловые полномочия.

## Доверенная конфигурация и запуск

Скопируйте `examples/config.json` **в каталог оператора**, задайте абсолютные
пути, имя модели и минимальные точные списки файлов. Конфигурация не должна
редактироваться аналитиком или браться из его JSON. `repository`, `runs_dir`
и `runtime_root` должны быть непересекающимися каталогами.

```bash
.venv/bin/python -m coder_agent \
  --config /absolute/private/coder-config.json \
  --input agents/developer/examples/task.json \
  --output /absolute/private/result.json
```

`--config` можно заменить переменной `CODER_AGENT_CONFIG`; тогда доступен
проектируемый интерфейс `python -m coder_agent --input task.json --output result.json`.
После установки также доступна команда `coder-agent`. Без `--output` JSON идёт
в stdout. Выходной файл должен быть новым и находиться вне исходного репозитория
и runtime; существующие файлы не перезаписываются. Коды выхода: 0 — `COMPLETED`,
1 — структурированный отрицательный результат, 2 — ошибка CLI/конфигурации/вывода.
При невозможности записать `--output` результат выводится в stdout.

Программный вызов:

```python
from pathlib import Path
from coder_agent import CoderAgent, Config

config = Config.model_validate_json(Path("/private/config.json").read_bytes())
agent = CoderAgent(config)
result = agent.run(Path("task.json").read_bytes())  # также dict или Task
print(result.model_dump_json(indent=2))
state = agent.status(result.run_id)
```

`Engine` — заменяемый Python Protocol. Передача `engine=` предназначена только
для доверенного интеграционного кода и тестов: такой адаптер сам отвечает за
изоляцию. У CLI/входного JSON нет режима отключения песочницы.

## Контракты и статусы

Вход версии `1.0` приведён в `examples/task.json`. Все поля примера обязательны.
Лишние поля, нестрогие типы (`"1"`/`true` вместо целого attempt), неизвестная версия
или операция, пустые инструкции/requirements/criteria, повторные ключи JSON
отклоняются. Максимальный размер задания — 64 KiB; Python-вход ограничен так же.

Поддерживаются `create` и `modify`, UTF-8 файлы и относительные POSIX-пути из
ASCII-букв, цифр, `_`, `-`, `.`, `/`. Не поддерживаются wildcard, абсолютные пути,
`..`, пустые/`.` сегменты, обратные слеши, symlink, hardlink, устройства и FIFO.
Для `modify` файл должен существовать и входить в read_files. Для `create` он
должен отсутствовать. Операции, дубли целей, лишние разрешённые записи и конфликт
«файл/каталог» проверяются до запуска. Чтение файлов идёт через `openat`/dir-fd и
`O_NOFOLLOW`, без следования symlink даже при подмене родительского каталога.

`read_files` и `allowed_write_files` плана сужают точные списки доверенной Policy.
Обычный конфигурационный файл можно изменять только при явном разрешении
оператора **и** плана. Секреты, `.git`, `.ssh`, `.aws`, `.env*`, базы данных,
`AGENTS.md`, конфигурации/плагины OpenCode и другие защищённые пути запрещены
даже при включении в оба списка. Запрет по имени консервативен и может требовать
ручного выполнения задачи над файлом с таким именем.

| Статус | Значение |
| --- | --- |
| `COMPLETED` | Движок сообщил о завершении, каждый запланированный файл изменён, аудит границ прошёл. Это **не** подтверждение корректности решения или прохождения тестов. |
| `NEEDS_CLARIFICATION` | Конфликт/неполнота плана, отсутствие ожидаемого файла/изменения, запрос дополнительного решения или файла от движка. |
| `INVALID_INPUT` | JSON не соответствует строгой схеме. OpenCode не запускался. |
| `FAILED` | Ошибка/тайм-аут движка, превышение журнала, некорректный финальный ответ. |
| `BLOCKED` | Недоступны runtime, OpenCode, Bubblewrap, модель, авторизация или шлюз; ошибочны модельные лимиты, исчерпан бюджет, повреждено хранилище, выполняется другая попытка либо снимок устарел. |
| `SECURITY_VIOLATION` | Путь/операция превышает полномочия, обнаружено нарушение при аудите файлов или сообщённых tool events. |

Произвольные противоречия в естественном языке нельзя доказательно выявить
Pydantic-валидацией. Их должен сообщать OpenCode через строгий финальный JSON
`NEEDS_CLARIFICATION`; его сообщение и требуемые файлы попадают в `error`.
Автоматически расширять список доступа агент не умеет.

## Изоляция и её проверенные границы

Вместо полной worktree создаётся разрешённый заданием **выборочный снимок**
текущих файлов рабочего дерева, включая локальные изменения. Git-метаданные,
остальные исходники, секреты и исходный репозиторий в песочницу не монтируются.
Ни одна Git-команда не выполняется новым CoderAgent.

Bubblewrap создаёт отдельные user/PID/mount/network/IPC/UTS namespaces;
внутри UID/GID 65534, capabilities сброшены, дальнейшие user namespaces запрещены.
Виден только подготовленный runtime read-only, приватные `/proc`, `/dev`,
временные home/tmp, управляющие файлы read-only и снимок `/workspace` read-only.
**Только каждый явно разрешённый файл** перекрывается отдельным writable mount.
Новые файлы заранее создаются как пустые mount targets, но в baseline остаются
отсутствующими. Читаемые контекстные файлы недоступны для записи на уровне ОС.

Команды shell, Git, тесты, делегирование, MCP, skills, LSP, форматтеры и web-tools
запрещены конфигурацией OpenCode. Runtime-сборщик также не копирует shell/Git.
Это дополнительные меры; файловые и сетевые границы обеспечиваются namespaces
и монтированиями, а не текстом промпта. Недоступность защиты даёт `BLOCKED`.
Для OpenCode 1.19.4 точные файловые permissions включают варианты относительно
`/workspace`, глобального worktree `/` (снимок не содержит `.git`) и абсолютный
путь. Wildcard-разрешения на исходники не добавляются.

Время ограничивает хостовый supervisor; превышение срока/журнала завершает
группу процессов. Bubblewrap уничтожает приватный PID namespace, в том числе
детей с собственной сессией. Есть RLIMIT_CPU (на процесс), NPROC (на host UID),
NOFILE, CORE=0, FSIZE (не менее 32 MiB для служебных БД OpenCode); home и tmp
ограничены по 256 MiB. Отдельно ограничены размеры входных/выходных исходников.
`steps` ограничивает агентные итерации, шлюз — обращения/токены ответа.
**Общего жёсткого лимита RAM, совокупного CPU и денежных затрат здесь нет**;
для этого оператору нужен внешний cgroup/job limit и бюджет провайдера.

После выполнения проверяются содержимое, режимы, типы и набор файлов, включая
неучтённые Git файлы и новые каталоги. Проверяются и сообщённые OpenCode tool
events. Это не полный аудит syscalls: заблокированную и скрытую движком попытку
невозможно гарантированно классифицировать по журналу. Проверка diff не заменяет
песочницу. Разрешённые исходные файлы перечитываются для обнаружения устаревания.

Доверенная база: оператор, конфигурация, Python-компонент, runtime/OpenCode,
модельный шлюз, ОС и её механизмы изоляции. Каталог runs должен быть приватным
и не изменяться сторонними процессами того же пользователя. Защита от root,
уязвимостей ядра или злонамеренного оператора не заявляется. Секреты внутри
обычно названного явно разрешённого исходника не обнаруживаются по содержимому:
оператор обязан выбирать несекретные файлы. Их текст поступает модели.

## Повторы, состояние и артефакты

`flock` блокирует пару `(workspace_id, task_id)` независимо от attempt. Блокировка
автоматически освобождается при смерти процесса. На локальной POSIX FS receipt
записывается до начала редактирования. Не используйте общий NFS/object storage.

* Тот же план с тем же attempt возвращает прежний окончательный Result/run_id
  после проверки привязки к доверенному repository/policy и целостности артефактов.
* Изменённый план с прежним attempt возвращает `NEEDS_CLARIFICATION`.
* Незавершённый receipt не возобновляется: `BLOCKED`, требуется осмотр и новый attempt.
* Новый attempt всегда создаёт свежий снимок исходника; частичные правки не копируются.
* Проверка `--status RUN_ID` возвращает `RUNNING`, `FINISHED` с Result либо
  `INTERRUPTED`; при повреждении состояния — `BLOCKED`. Блокировка содержит UUID
  владельца, поэтому новая попытка не делает старую прерванную попытку «живой».
  Эта проверка никогда не запускает движок и не изменяет lifecycle тикета.

```bash
.venv/bin/python -m coder_agent --config /private/config.json --status RUN_ID
```

Каждый новый запуск получает UUID и приватный каталог `runs_dir/runs/RUN_ID/`.
Отчёты публикуются атомарно с fsync, receipt создаётся эксклюзивно и не заменяет
существующую попытку. Перед `COMPLETED` синхронизируются выходные файлы/каталоги
и patch; `outputs.json` сохраняет SHA-256, размеры и режимы снимка, digest patch.
При replay повреждение, исчезновение или изменение этих артефактов даёт `BLOCKED`
без запуска движка. `outputs.json` — внутренний seal хранилища.
Старые результаты без seal/привязки к repository/policy не принимаются как
проверенный успех: нужен осмотр и новый attempt. Автоматической миграции нет.
Ошибки задания также получают отчёт.
Если недоступны сама конфигурация или хранилище, CLI сообщает ошибку в stdout;
сохранить отчёт на недоступном диске невозможно.
`run()` возвращает структурированный `BLOCKED` и без ссылок на успешные артефакты,
даже если сохранение самого отчёта невозможно. Ошибки конфигурации/создания
ReportStore при конструировании `CoderAgent` по-прежнему должны обрабатываться
вызывающим Python-кодом; CLI уже переводит их в JSON.

В JSON нет абсолютных путей к артефактам, только безопасные `RUN_ID/name`:

| Идентификатор | Файл относительно `runs_dir/runs/RUN_ID` |
| --- | --- |
| `report` | `report.json` |
| `log` | `engine.log` |
| `capabilities` | `capabilities.json`: проверенная версия и run --help |
| `manifest` | `manifest.json`: исходные SHA-256 и режимы |
| `patch` | `changes.patch`, только при COMPLETED |
| `files` | `workspace/`, только при COMPLETED |

Снимок содержит также разрешённый контекст: забирать нужно только `changed_files`.
При отрицательном результате снимок остаётся для диагностики, но ссылок `files`
и `patch` нет. Оркестратор обязан проверять статус перед использованием артефактов.
Удаление/retention каталогов выполняет внешний владелец хранилища.

## Проверки и известные ограничения

Базовый прогон перед аудитом 26 октября 2026: **96 тестов — OK, без пропусков**
при разрешённых namespaces. В ограниченной внешней среде было 88 выполненных
тестов с 5 отметками skip. Итоговые результаты исправленной версии и полный
перечень изменений приведены в [AUDIT_REPORT.md](AUDIT_REPORT.md).
Среда: Python 3.14.4, Pydantic 2.14.1, Bubblewrap 0.11.1.

```bash
.venv/bin/python -m unittest discover -s agents/developer/tests -v
# В окружении с разрешёнными namespaces; запрещает тихий пропуск sandbox-тестов:
CODER_REQUIRE_SANDBOX=1 .venv/bin/python -m unittest discover -s agents/developer/tests -v
# Только unit-тесты движка: не требуют ни bwrap, ни OpenCode:
.venv/bin/python -m unittest discover -s agents/developer/tests -p test_engine.py -v
# Настоящие OS-пробы с fake OpenCode:
CODER_REQUIRE_SANDBOX=1 .venv/bin/python -m unittest discover -s agents/developer/tests -p test_sandbox_integration.py -v
# Опционально: настоящий CLI + локальный scripted API, без настоящей LLM:
CODER_REQUIRE_SANDBOX=1 CODER_TEST_OPENCODE=/absolute/trusted/opencode \
  .venv/bin/python -m unittest discover -s agents/developer/tests -p test_real_opencode_integration.py -v
```

Тесты используют временные Git-репозитории, fake OpenCode, настоящий Bubblewrap
и локальный HTTP/Unix gateway с фиктивным ключом. Проверяются строгий контракт,
пути/секреты/конфиги, сохранность исходного репозитория, закрытая сеть, UID,
запрещённые записи, create/modify, тайм-ауты и дети с отдельной сессией, ошибки,
повторы/конкуренция/прерванные попытки, CLI и совместимость старых тестов.
Без разрешения namespaces соответствующая группа явно пропускается; при
`CODER_REQUIRE_SANDBOX=1` это ошибка. Сетевые тесты требуют локальных сокетов.
Unit-тест отсутствия OpenCode явно подставляет доступные fake Python/Bubblewrap,
поэтому не зависит от порядка отсутствующих компонентов на машине.

Настоящий standalone **OpenCode v1.19.4** загружен из официального релиза,
SHA-256 сверён с официальной метаинформацией. Он действительно изменил только
разрешённый Python-файл во временном репозитории через `read`/`edit` внутри
Bubblewrap; запрещённый вызов `write` отклонён. Локальный API в этой проверке —
scripted имитатор ответов модели. Отдельно **настоящая локальная `qwen3.5:9b`
через Ollama проверена** на точной правке файла, исправлении Python-функции
с независимой проверкой поведения и обычном CLI через постоянный шлюз.
Выбранный профиль работает на RTX 4060 Laptop с контекстом 8192 и output 2048;
полный регрессионный прогон — 176 PASS без пропусков.
Команды и доказательства приведены в [LOCAL_MODEL.md](LOCAL_MODEL.md).
Само наличие `CODER_TEST_OPENCODE` подтверждает только scripted API, а не новую
модель или другой профиль.
Перед каждым фактическим запуском адаптер проверяет
изолированные `--version` и `run --help`, сохраняет их и допускает только
поддержанные `--format`, `--model`, `--agent`. Используются документированные
[CLI-параметры](https://opencode.ai/docs/cli/),
[permissions](https://opencode.ai/docs/permissions/) и
[agent.steps](https://opencode.ai/docs/agents/#max-steps), выдуманных флагов нет.
`--help` может идти в stderr: это учитывается. stdout JSON-events и stderr
диагностика разделены, но общий журнал ограничен одним `max_log_bytes` на всю
попытку, включая preflight. Фактически применённые permissions проверены
реальным вызовом инструментов, а не только наличием CLI-флагов.

Файловые mountpoints допускают запись на месте, но запрещают unlink/rename и
атомарную замену файла. Если версия OpenCode использует только atomic replace,
она завершится ошибкой; защита автоматически не ослабляется. Установленную
версию нужно проверить с реальной моделью на игрушечном репозитории.

Точный смысл `target`/`requirements` и отсутствие лишних изменений **внутри
разрешённого файла** зависят от движка и независимой последующей проверки.
CoderAgent сам не исполняет Miminet, его тесты, миграции или критерии приёмки.
Патч предназначен для ревью; `files` — авторитетный артефакт также для пустого
создаваемого файла, который не выражается обычным unified diff.
